Slide 3

REST APIs have long operated from these implicit agreements. Requests are sub-second, so your gateways, your load balancers, and your clients all carry timeouts tuned for milliseconds. Requests are stateless, so any replica can serve any request. Requests are deterministic, so a retry is a repeat. A repeat of the same input and expected output. And requests are stable, behavior only changes when you deploy. Pretty intuitive, right? Then the bombshell, LLM calls, entered the Villa and started challenging everything we know about our connections. (I don't watch love island but it still made for a supreme metaphor here) So LLM calls meant one request into a model takes minutes while also answering differently every time, quietly breaking all four agreements.

Slide 4

The first to fold is duration. Every timeout standing between your user and the model, the load balancer, the gateway, the client itself, was tuned for a world where requests finish in under a second. So a five-minute request trips them by design. Nothing is misconfigured, the stack is doing exactly what it was told. And when it trips, the failure splits in two. The client sees a dead connection and gives up, while the work has no idea and keeps going. Since there aren't any errors firing anywhere useful, the first person to notice is your user. And the whole time, the worker is still spending tokens finishing an answer that no longer has anywhere to arrive. You paid full price for a response no one received.

Slide 5

The second failure I call crash amnesia, where the work dies while the client is still waiting. In my previous setup, recovery was hand-rolled using a LangGraph error handler. It counts retries in state, and when the retries run out, the best it can do is send an apology message. Everything it's protecting lives in the same process it dies with, so a worker dying at room two of three restarts from zero. In this case, the user waits twice, you pay twice.

Slide 6

Then retries stop meaning what they used to. Model output is non-deterministic, the same input does not produce the same output, and that quietly breaks a contract we've trusted for decades.

Slide 7

And the last assumption to fall is stability. Models deprecate, prompts change weekly, providers have regional bad days, and your deploy cycle moves at none of those speeds. If the model name and the prompt are hardcoded, every prompt tweak is a deploy and every provider incident is an outage. The most volatile parts of your system are the ones with no lever attached. Keep that one in your pocket, it comes back as the third play.

Slide 8

So the answer starts with a bit of reframing. Instead of viewing it as an API, view it as a workflow with an HTTP face. Then the HTTP layer keeps exactly four jobs, it starts work, it reports progress, it accepts decisions, and it delivers results. Everything else, the state, the retries, the memory of what's already finished, moves into a durable execution layer, or a runtime whose whole purpose is to make progress survive the disruption of any single process. Every failure now has a correlated fix.

Slide 11

So the lingering principles here are make it survivable, which we just witnessed with the crash demo, the next part is make it visible, what new metrics should be exposed so you still have insight while you wait, and lastly make it steerable, if it's going off the rails can you nudge it in the right direction, can it fail gracefully to an older working variation.

Slide 12

The first part of making it survivable is never letting one request carry minutes of work. A request's only job should be to hand back an ID and get out of the way, so the workflow can do its thing.

Slide 13

If you remember before, the retry logic was a LangGraph handler where I had to consider the edge cases, here we see it replaced by a retry policy. So all that plumbing gets offloaded without compromising reliability. This works for situations where retries are more like a rerolling of the dice with non-deterministic outputs. And since results are checkpointed, a retry only ever re-rolls the step that failed, never an answer we already have.

Slide 14

Then there's the human-in-the-loop component that also requires the same courtesy of still running even when the worker crashes. This all centers around survivability.

Slide 15

For making it visible, traditional RED metrics still apply, but a model call adds three dimensions, cost per call, quality of output, and which prompt and model version served it. An LLM call can succeed at the HTTP layer and fail at the semantic layer.

Slide 16

Now how do we steer it, by putting the most risky things, the model, the prompt, the parameters, behind runtime levers. Externalize them, version them, and one mechanism buys you three capabilities. You can canary a change on a slice of traffic and roll it back in one click. You can decide at runtime which traffic gets which model. And during a provider incident, one targeting rule downgrades low-priority traffic to a cheaper variation instead of failing everyone.

Slide 17

So here's the durable execution landscape. They all handle their own version of checkpointed side effects, parking for a human, and fan-out. Live progress queries and encrypted history come built in on some of these and do-it-yourself on others. The real choice is operational posture, run it yourself, managed JSON, a single binary, or just a library. The playbook is pretty much the same everywhere.

Survivable, visible, steerable. Classic API operations spent decades making calls short, uniform, and repeatable.
